# Рабочая среда разработки

Эта инструкция описывает обычный цикл работы над ботом: разработка и проверка на Mac, хранение исходников в GitHub, запуск рабочего экземпляра на Windows.

## Карта проекта

```text
api/                 HTTP-точка входа для Vercel
src/
  app.ts             запуск HTTP-приложения
  polling.ts         запуск бота в режиме long polling
  commands/          команды и сценарии Telegram
  actions/           действия из карточек и списков
  clients/           клиенты GitHub, Google Calendar и AI-провайдеров
  core/              конфигурация, типы, журналирование и ошибки
  middlewares/       проверка доступа и обработка обновлений
  services/          логика задач, меню, календаря, голоса и интеграций
  views/             тексты и клавиатуры Telegram
  utils/             общие вспомогательные функции
  scripts/           служебные скрипты проекта
scripts/             внешние скрипты, включая локальную расшифровку голоса
docs/                инструкции по отдельным возможностям
```

Обычно новую функцию удобно вести по цепочке:

1. Интерфейс Telegram — `src/commands/`, `src/actions/`, `src/views/`.
2. Правила и работа с данными — `src/services/`.
3. Внешний сервис — `src/clients/`.
4. Регистрация точки входа — `src/app.ts` или `src/bot.ts`.
5. Проверка — тест рядом с изменённым модулем, затем общие проверки ниже.

Не переносите файлы между слоями только ради порядка: сначала выделите границы ответственности и убедитесь, что импорты и сценарии покрыты проверками.

## Первый запуск на Mac

Из папки проекта:

```bash
bun install
cp .env.example .env
```

Заполните только нужные значения в `.env`. Не отправляйте этот файл, токены и JSON-ключи в GitHub. Для локального polling-режима используйте отдельного тестового Telegram-бота, если он настроен.

Запуск локального режима разработки:

```bash
bun run dev
```

Остановить сервер: `Ctrl+C`.

## Перед передачей изменений на Windows

После правки сначала проверьте проект на Mac:

```bash
bun run lint
bun run build
bun test
```

Для быстрой проверки одного набора тестов:

```bash
bun test src/commands/menu.test.ts
```

Если проверка не прошла, сначала обновите локальную ветку и убедитесь, что файл теста и проверяемый модуль относятся к одному коммиту. Ошибка вида «Export named … not found» часто означает рассинхрон между тестом и исходным файлом.

После успешных проверок отправьте изменения в используемую ветку. На Windows обновляйте рабочую копию только после этого:

```powershell
cd C:\Users\iliay\task-manager_01
git pull --ff-only origin feature/daily-copilot-now
```

Затем перезапустите задачу планировщика `TaskManagerBot`. Не редактируйте исходники отдельно на сервере: изменения должны идти через GitHub, чтобы Mac и Windows не расходились.

## Полезные правила проекта

- Локальные импорты TypeScript заканчиваются на `.js`, например `../services/foo.js`.
- Запускайте форматтер/линтер после изменений: здесь используется Biome (`bun run lint`), не ESLint.
- Перед крупным изменением найдите похожий сценарий и его тесты.
- Секреты, локальные логи, модель Whisper и пользовательские данные не добавляйте в коммиты.
- Если меняются кнопки, проверяйте не только текст сообщения, но и callback, возврат назад и повторное открытие экрана.
- Если изменяется сценарий сохранения, проверьте отмену, повторное нажатие и работу при отсутствии сети/API.
